# Бэкенд футбола — проект

Дата: 2026-11-19. Статус: на согласовании.

## Зачем

Экраны «Сегодня» и «Карточка матча» показывают матчи, счёт, статус и таблицы. Источник — football-data.org, но у него лимит ~10 запросов в минуту на ключ, общий для всех пользователей (D8). Поэтому данные забирает сервер по расписанию, а приложение читает готовые таблицы Supabase.

**Цели**
- Матчи с вчера до +7 дней по выбранным турнирам: время, статус, счёт, тур.
- Турнирные таблицы этих турниров.
- Свежесть счёта во время матча — около минуты (плюс задержка самого бесплатного тарифа).
- Расход лимита не зависит от числа пользователей.

**Не цели** (отдельные задачи позже)
- Клиентский код в приложении.
- НХЛ (пока клиент ходит в API НХЛ напрямую, D8).
- Пуши «за 15 минут», закладки, подборки редакции.
- Ввод русских названий команд — только место под них.

**Анти-цели**
- Ключ football-data.org попадает в приложение или в git.
- Кто угодно с публичным anon-ключом может дёргать синхронизацию и сжечь лимит.
- Приложение может писать в эти таблицы.

## Подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| **A** ✅ | pg_cron раз в минуту вызывает Edge Function `sync-football`, она пишет в таблицы | Лимит не зависит от пользователей; данные всегда свежие; тот же cron потом для пушей | Синхронизация идёт, даже когда приложение никто не открывает |
| B | Edge Function-прокси с кешем на минуту | Без cron | Холодный первый запрос, всплески упираются в лимит, для пушей cron всё равно нужен |
| C | pg_cron + HTTP и разбор JSON прямо в SQL | Меньше частей | Логика на plpgsql, плохо тестируется |

Выбран **A** (решение пользователя).

## Как устроено

```
pg_cron (каждую минуту)
  └─ net.http_post → Edge Function sync-football  (заголовок x-sync-secret)
        ├─ GET /v4/matches?dateFrom=вчера&dateTo=+7&competitions=…   (1 запрос)
        │     upsert competitions, teams, matches
        └─ GET /v4/competitions/{code}/standings                      (0–2 запроса)
              upsert standings
приложение ── PostgREST, anon-ключ, только SELECT ──> таблицы
```

### Турниры

По умолчанию: **PL, PD, BL1, SA, FL1, CL** (топ-5 лиг Европы + Лига чемпионов, как в концепте). Список хранится в таблице `competitions` полем `enabled`, меняется без деплоя. Остальные турниры бесплатного тарифа (EC, WC, DED, PPL, ELC, BSA) заводятся выключенными.

### Расписание и расход лимита

Каждый запуск решает сам, что делать:
- **Матчи** — если есть матч в игре или начинающийся в ближайшие 15 минут, запрос каждый запуск (раз в минуту). Иначе — раз в 15 минут.
- **Таблицы** — сначала турниры, где после последнего обновления таблицы закончился матч; иначе самая старая таблица, если ей больше 6 часов. Не больше 2 запросов за запуск.

Итого максимум 3 запроса в минуту при лимите 10 — остаётся запас на ручные запуски и ретраи. Если football-data.org ответил 429, запуск завершается, остальное сделает следующий.

### Таблицы (схема `public`)

- `competitions` — `id` (id football-data), `code`, `name`, `name_ru`, `emblem_url`, `enabled`, `standings_updated_at`.
- `teams` — `id`, `name`, `short_name`, `tla`, `name_ru`, `short_name_ru`. Поля `*_ru` заполняем вручную; синхронизация их не трогает, приложение показывает `*_ru`, если есть, иначе английское.
- `matches` — `id`, `competition_id`, `utc_date`, `status`, `matchday`, `stage`, `group_name`, `home_team_id`, `away_team_id`, `home_score`, `away_score`, `winner`, `source_updated_at`, `synced_at`. Индекс по `utc_date`.
- `standings` — строка на команду: `competition_id`, `stage`, `group_name`, `position`, `team_id`, `played`, `won`, `draw`, `lost`, `goals_for`, `goals_against`, `goal_difference`, `points`, `form`. Таблицу турнира заменяем целиком за один раз.
- `sync_state` — `key`, `value jsonb`, `updated_at`: время последних запросов, последняя ошибка.

**Доступ (RLS):** `anon` и `authenticated` — только `SELECT` из `competitions`, `teams`, `matches`, `standings`. `sync_state` клиенту не виден. Пишет только функция через service role.

### Секреты

- `FOOTBALL_DATA_KEY` — ключ football-data.org, в секретах Edge Functions.
- `SYNC_SECRET` — случайная строка: в секретах функции и в Vault базы; pg_cron передаёт её заголовком, функция без него отвечает 401. JWT-проверку у функции выключаем, иначе её мог бы вызвать любой с публичным anon-ключом.

Ключ football-data.org ты задаёшь сам командой `supabase secrets set` — я его не ввожу и не вижу.

### Код и проверки

```
supabase/
  config.toml
  migrations/<время>_football.sql      таблицы, RLS, индексы
  migrations/<время>_football_cron.sql pg_cron + pg_net, расписание
  functions/sync-football/
    index.ts      HTTP-обработчик: проверка секрета, запросы, запись
    mapping.ts    чистые функции: JSON football-data → строки таблиц
    plan.ts       чистая функция: что запрашивать в этом запуске
    *_test.ts     deno test на mapping и plan
```

- `mapping.ts` тестируется на ответах из `tribuna_api_report/raw/` (уже в репозитории).
- `plan.ts` тестируется на наборах «есть live / нет live / таблица устарела / только что закончился матч».
- Миграции проверяем локально (`supabase start`, `supabase db reset`), включая то, что anon не может писать.
- Сквозной прогон — на `tribuna_db` с настоящим ключом: ручной вызов функции, затем проверка строк в таблицах.

## Что решено мной (поправь, если не так)

1. Турниры по умолчанию — PL, PD, BL1, SA, FL1, CL.
2. Окно матчей — вчера … +7 дней (полоса дней на «Сегодня» — неделя).
3. Частота: раз в минуту при live, иначе раз в 15 минут; таблицы — после матчей или раз в 6 часов.
4. Русские названия — ручные поля в `teams`, без автоперевода.
5. Защита функции — общий секрет в заголовке, а не JWT.
6. Миграции — файлами в `supabase/migrations/`, применяются на `tribuna_db` через Supabase CLI.

## Что остаётся исполнителю

Точные имена колонок и типов, обработка ошибок сети, формат записи в `sync_state`, структура тестов.
